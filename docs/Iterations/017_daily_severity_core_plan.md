## Preserved semantic contract

| Requirement | Iteration 017 treatment |
|---|---|
| Daily built-in severity | Integers 0=Not present, 1=Mild, 2=Moderate, 3=High. Nine PHQ values sum to 0–27; seven GAD values sum to 0–21. No presence/frequency remapping. |
| Missing versus zero | Explicit 0 is answered. Null/missing response cannot yield a valid daily total or be filled with 0. This is validation, not permission to store partial check-ins. |
| Period severity | Future analytics use recorded days only, per-item sums/counts; missing days are excluded and disclosed. No period API/calculation is implemented here. |
| Derived 14-day presence | Separate future result: severity >0 counts one present recorded day; 0→0, 1–6→1, 7–11→2, 12–14→3; sum mapped scores and disclose recorded/missing coverage. Empty coverage must not imply absence. This remains a requirement, not daily-score behavior. |
| Item 9 | Only trusted built-in `phq9` / `phq9.item9` can bind its safety behavior. Labels, ninth position or matching custom IDs cannot establish privilege. Its severity contributes normally to the PHQ daily sum. No safety engine/side effect is implemented here. |
| Custom questionnaires | Built-in service rejects unsupported/custom definitions; it does not treat them as PHQ/GAD or infer interpretation. A future custom engine may implement explicitly approved deterministic rules, never invented clinical categories. |

The pinned Python reference and Iteration 016 fixtures agree on valid daily values. The actual `calculate_questionnaire_total` validates definition/count and rejects None as an unsupported response. The proof's Python adapter catches that rejection and projects `unanswered / total null`; it is **not** proof of a production partial-record policy. Product semantics outrank any helper permissiveness, float artifact or adapter projection. Historical stored PHQ/GAD values remain severity; no internal version split is introduced into ordinary product vocabulary.

## Proposed domain interfaces and ownership

Dan approved the complete/incomplete/invalid domain contract on 2026-10-10. The outcomes and precedence below are settled requirements; interface names and detailed error codes remain implementation design choices for review. This is not Dart source and does not freeze UI messages or storage schema.

| Interface/type | Proposed responsibility and invariant |
|---|---|
| `BuiltinQuestionnaireId` | Closed PHQ-9/GAD-7 identity type; labels and arbitrary strings do not create a trusted catalog definition. No extensibility by untrusted behavior flags. |
| `BuiltinQuestionId` / `BuiltinCatalog` | Immutable reviewed identity sets `phq9.item1..9`, `gad7.item1..7`, canonical order and questionnaire membership. No clinical wording, persistence revision or migration map. Reject reserved identity claims from custom-origin adapter input. |
| `SeverityValue.fromInt` | Validates integer 0–3; immutable. No clamp, string parsing, boolean acceptance or float conversion. Malformed JSON is rejected at the typed conformance edge before construction. |
| `DailySeverityRequest` | Questionnaire identity and immutable list of keyed answers, each with integer-or-unanswered input. Copy caller collections; require unique recognized IDs and exact expected membership for a complete result. Never rely on incoming list position to infer question identity. |
| `DailySeverityService.evaluate` | Synchronous pure function/service. Inspect all supplied answers for validity before deciding completeness. Invalid input takes precedence over missing required answers. Calculate one integer sum only after validation and completeness succeed. No IO, time, database, callback, channel or clinical side effect. |
| `DailySeverityResult` | Immutable sealed result family with exactly complete, incomplete and invalid variants. Exhaustive typed handling; no ambiguous status strings or nullable total on the common interface. |
| `CompleteDailySeverity` | Questionnaire identity, immutable validated responses and integer total; no interpretation/category/safety decision fields. Valid total is never nullable. |
| `IncompleteDailySeverity` | At least one required answer is absent or explicitly unanswered, with no invalid supplied answer or structural/admission error. Immutable missing question identities; no total property. It cannot represent a persisted partial assessment. |
| `InvalidDailySeverity` | At least one supplied answer violates its definition, or input has a structural/admission error such as unsupported identity or unexpected/duplicate/foreign questions. Immutable explicit typed validation errors; no total property. Missing answers cannot downgrade this outcome to incomplete. |
| Daily conformance adapter | Resolve fixture definition/order to reviewed identities; perform strict JSON type checks; translate result to the reviewed fixture vocabulary. Only harness may read JSON/run Python/write fictional evidence. Expectations never enter the calculator. |

Public constructors must not let consumers fabricate an inconsistent complete score. Copy input/result collections and expose immutable views; caller mutation must not change evaluation. Keyed response reordering preserves the outcome and total. Validation errors have typed codes, relevant item identity and deterministic ordering; avoid embedding raw sensitive values in diagnostic messages. This requirement does not define duplicate-day merge, edit behavior or incomplete-check-in persistence.

An omitted required item and an explicitly unanswered required item both count as missing. A shorter answer list caused solely by omitted required answers is incomplete, not invalid. Extra/unknown/foreign or duplicate identities are invalid; supplied booleans, floats, strings (including blank strings and "0"), unsupported types and integers outside 0–3 are invalid rather than missing. The conformance edge distinguishes absent/null answers from malformed structures. A missing answer plus an invalid supplied answer returns invalid with explicit errors: never stop at the first missing answer. Do not substitute zero, compute or expose partial totals, or normalize invalid values into unanswered values.

The historical proof's `status: unanswered` projection is confined to its conformance adapter, not the public domain API. Tagged JSON at the language-neutral test boundary may encode the three outcomes under a reviewed fixture contract; string serialization must not replace typed Dart results. Preserve raw Python rejection evidence separately: its count/None rejection does not supersede Dan's approved incomplete result. Map only reviewed missing-only inputs to incomplete in the oracle adapter; never convert a generic Python rejection into incomplete without independent validation.

No parser/serializer, Flutter, SQLite, FFI, `dart:io`, network, clock or process import enters `len_core` runtime. Test tooling may use separately approved dev dependencies; no dependency installation or production pin selection is authorized by this plan. Python is development reference tooling only, not successor runtime.

## Test strategy and acceptance

1. **Pure core unit tests:** factories, bounds, identity validation, omitted/null versus zero distinction and immutable inputs/results. Assert all three typed outcomes without rendering or filesystem access. Include mixed missing/invalid inputs in both orders, multiple validation errors and shorter missing-only lists. Verify exhaustive result handling and that incomplete/invalid variants expose no total.
2. **Deterministic invariant tests:** exhaustive valid GAD severity vectors (4^7=16,384) are practical; use fixed, reproducible PHQ vectors including single-item contributions and permutations. Independently sum validated integers in tests and assert range/additivity; do not call the implementation's helper to build expectations. No random dependency is necessary.
3. **Three-way daily conformance:** reviewed handwritten expectations, unchanged pinned Python and production Dart adapter must agree for supported complete inputs. For incomplete/invalid inputs, distinguish Python rejection from adapter projection; strict input validators must reject malformed types regardless of Python's low-level equality behavior. Keep expected/Python/Dart results and source/fixture hashes separate. Fault controls must catch wrong totals, zero-filled unanswered input and mismatches that both engines share.
4. **Architecture checks:** domain/service builds and tests without Flutter/SQLite/platform/IO dependencies; public boundary has no arbitrary behavior registration; approved package manifest/runtime import rules and no expected-output access.
5. **Progressive validation:** affected tests first, daily subsystem/conformance when stable, package suite and analyzer once at completion. No unrelated Len suite, Flutter/native build, previous proof rerun or fresh architecture experiment is necessary unless a specific interaction warrants it. Record exact counts and limitations; a plan contains no claimed new passing tests.

Acceptance requires all seven complete daily fixtures and the approved typed incomplete case to pass, all invalid-input/identity/mutation regressions to pass, independent arithmetic invariants to pass, and no clinical interpretation/safety action. Complete means every required answer is present and valid and the integer total is correct. Missing-only inputs return incomplete with exact missing identities and no total; any invalid supplied answer returns invalid with explicit errors and no total even when answers are also missing. No zero substitution, partial totals, coercion or ambiguous public status strings is permitted. All requests/results/error collections are immutable. Unsupported/custom data cannot become a builtin result. Preserve independent expected outcomes and raw Python behavior, explicitly reconciling approved semantics where Python rejection differs. Document the public contract, semantic basis, fixtures, source attribution, modified files, test results and unresolved semantics. No persistence decision, production Python or user-data changes.
